1. What is this?

This project is a small program that looks at crypto prices (Bitcoin, Ethereum, and so on) and tells you how risky a portfolio is.

Think of it like a weather forecast — but for your investments. You tell the program what coins you hold and how much of each, and it answers questions like:

  • "On a bad day, how much could I lose?"
  • "How bad would the worst day in 100 days look?"
  • "How much has this portfolio gone up or down over time?"

It comes in two flavours:

  • A web app that opens in your browser. Easiest.
  • A one-shot script that prints a summary and saves some files. Good for quick checks.

This guide covers both, but the web app is what we recommend.

You do not need to know any code. The whole setup is copy, paste, press Enter. We'll walk through every step.

2. What you need

  • A laptop running Windows, macOS, or Linux.
  • An internet connection (only for the first-time setup, and whenever you fetch fresh prices).
  • About 15 minutes of setup. After that, opening the app takes 5 seconds.
  • The project folder (named risk-management) saved somewhere on your computer — for example on your Desktop.
Heads up: we are going to use a tool called the Terminal. It looks like a black or white window where you type commands. Don't worry — you won't break anything by typing in it. Each command we use is shown in a dark grey box. You can copy it and paste it directly.

3. Install Python

Python is the language this program is written in. You only need to do this step once.

On Windows

  1. Open your browser and go to https://www.python.org/downloads.
  2. Click the big yellow "Download Python 3.x" button.
  3. Open the downloaded file (.exe).
  4. Important: on the first screen, tick the box that says "Add Python to PATH" at the bottom. Then click Install Now.
  5. When it finishes, click Close.

On macOS

  1. Open your browser and go to https://www.python.org/downloads.
  2. Click "Download Python 3.x".
  3. Open the downloaded .pkg file and follow the installer (just keep clicking Continue and Install).

On Linux

Python is usually already installed. If not, open a terminal and run: 

sudo apt update
sudo apt install python3 python3-venv python3-pip

Check that Python works

Open a terminal (next section explains how) and type: 

python3 --version

You should see something like Python 3.12.3. Any version starting with 3.10 or higher is fine.

If you see "command not found": Python wasn't added correctly. On Windows, re-run the installer and remember to tick "Add Python to PATH". On Mac, restart the Terminal.

5. Set up the project

These four steps prepare the project. Do them once. After that, starting the app takes a single command.

1

Go to the project folder

In the terminal, type cd (which means "change directory") followed by the path to where the risk-management folder lives. For example, if it is on your Desktop:

Windows:

cd Desktop\risk-management

macOS / Linux:

cd ~/Desktop/risk-management
Easy trick: in your file manager, open the risk-management folder, then drag and drop it into the terminal window after typing cd (with a space). The full path appears automatically.
2

Create an isolated workspace

We make a small "sandbox" so this project keeps its tools separate from the rest of your computer. 

python3 -m venv .venv

Wait until the prompt comes back. A new hidden folder called .venv appears in the project. You only do this once.

3

Activate the workspace

You do this every time you open a new terminal.

Windows (PowerShell):

.\.venv\Scripts\Activate.ps1

macOS / Linux:

source .venv/bin/activate

You'll know it worked when (.venv) appears at the beginning of the line in your terminal.

Windows only: if PowerShell complains about scripts being disabled, run this command first, then try again: 
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
Answer Y when it asks.
4

Install the project's tools

This downloads everything the program needs (about 200 MB of files). Only the first time. 

pip install --upgrade pip
pip install -r requirements.txt
pip install -e .

You'll see lots of messages scrolling. That's normal. When the prompt comes back without errors, you're ready.

You're done with setup. Next time you want to use the app, all you'll need is:
  1. Open the terminal
  2. cd into the project folder
  3. Activate the workspace (step 3)
  4. Run the app (next section)

6. Run the web app

With the workspace activated (.venv) visible in your terminal, type: 

streamlit run app.py

After a few seconds your browser opens automatically at an address like http://localhost:8501. That's the app.

To stop the app: go back to the terminal and press Ctrl + C. Close the browser tab if you wish.

Optional: the one-shot command-line demo

If you'd rather not use the web app, run: 

python run_demo.py

This single command does everything in one go: fetches prices, computes VaR / CVaR / drawdown and the new backtesting checks (Phase 3). It prints a summary in the terminal and saves every chart, table, and JSON file under the outputs/ folder. Open that folder in your file manager to see them.

7. Using the web app

The web app has a sidebar on the left for settings and a main area on the right for results. Here's what each part does.

The sidebar (left)

Data source Where to get prices. CoinGecko is free and reliable. If it ever stops working, leave the "Fall back to yfinance" box ticked and the app will switch automatically.

Start date / End date The time window to study. Longer windows give more data; shorter windows reflect recent conditions. 2021-01-01 to today is a good default.

Return method Leave this on simple unless you know what log returns are.

Initial capital Pretend you put this much money into the portfolio. Numbers later on (like dollar losses) use this amount.

Confidence level A slider from 80% to 99.9%. The higher you set it, the rarer (and worse) the loss the app reports. 95% is the standard.

Time horizon How many days into the future the loss applies to. 1 means a one-day loss. The number for longer horizons is an approximation, so don't go past a few weeks.

VaR / CVaR methods Tick which methods you want to compare. Leave them all on the first time.

The portfolio editor

A small table where you list each coin you own and how much of the portfolio it represents (its weight). The default is BTC 50% / ETH 30% / SOL 20%. To change:

  • Click a number in the Weight column and type a new one.
  • Add a row by scrolling to the bottom of the table — there is an empty row marked "+".
  • Delete a row by selecting it and pressing Delete.

Weights should add up to 1.0 (i.e. 100%). If they don't, leave "Auto-normalize weights" on in the sidebar — the app will scale them for you.

The Run button

After every change to the sidebar or the portfolio table, click Run risk analysis. The app fetches the prices, does the math, and updates everything below.

The result tabs

TabWhat it shows
Risk summary A full table of every risk number for your portfolio. There is a "Download CSV" button under it.
Distribution A histogram of daily returns. Red dashed line = VaR threshold. Red shaded area = CVaR tail. The most informative single chart.
Cumulative How the portfolio's total return changed over time.
Drawdown How far the portfolio dropped below its previous high. Red valleys are bad periods.

Instead of looking at the past, it simulates thousands of plausible futures from a joint return model (Normal or Student-t), then reports the simulated VaR and CVaR, plots the loss distribution, draws a fan of portfolio value paths over the next 30 days, and compares Historical / Gaussian / Cornish-Fisher / Normal MC / Student-t MC side-by-side in one table. Pick a scenario source (Historical / Normal MC / Student-t MC), an objective (minimum-CVaR, max return under a CVaR cap, minimum CVaR for a target return, or the full CVaR efficient frontier), and constraints (long-only, min/max weight, optional cash). The app solves the optimisation, shows the new weights, and puts them head-to-head with your current portfolio. See section 8 for what the numbers mean.

The Backtesting tab — how to use it

After you click Run risk analysis, open this tab and:

  1. Pick a VaR method to test, or choose "Compare All" to see all three side by side.
  2. Choose a confidence level (95% is the standard) and a rolling window (252 days is the regulatory standard — about one trading year).
  3. Choose a Horizon (days):
    • 1 — classic one-step-ahead daily backtest. VaR forecast is for tomorrow, realised return is tomorrow's return.
    • 7 — weekly. VaR forecast is for the next 7 days, realised return is the realised 7-day return. The chart and table both say "7-day VaR Backtest".
    • 10, 30, … — for monthly or regulatory horizons.
    Picking the horizon to match your headline VaR cards keeps the two views consistent.
  4. Click Run Backtest.

The results stay on screen even if you switch tabs or download files. Every chart and table can be downloaded with the "⬇️ Download" buttons.

The Monte Carlo tab — how to use it

Backtesting checks the past. Monte Carlo asks "what could plausibly happen next?" by simulating thousands of futures. Open the 🎲 Monte Carlo Scenario Engine tab after you've run a risk analysis and:

  1. Pick a Distribution:
    • Normal — assumes returns are bell-shaped (light tails). Usually too optimistic for crypto.
    • Student-t — heavy-tailed, much closer to what crypto markets actually do. Recommended.
    • Compare Normal vs Student-t — runs both and overlays them so you can see the difference.
  2. Choose Number of scenarios (5,000 is a good default; more is smoother but slower) and a Horizon (days). The horizon defaults to whatever you picked in the sidebar.
  3. If you picked Student-t, set df (degrees of freedom). 5 is a sensible default for crypto. Lower = heavier tails.
  4. Set n_paths and Path horizon (days) for the portfolio-value path chart. 500 paths over 30 days is the default.
  5. Click Run Monte Carlo.

You'll see five KPI cards (MC VaR, MC CVaR, mean / worst simulated return, number of scenarios), the simulated return distribution with VaR and CVaR markers, a fan chart of plausible portfolio paths over the next month, and a final comparison table that lines up Historical, Gaussian, Cornish-Fisher, Normal MC, and Student-t MC at the chosen horizon — so you can immediately see which method is the most conservative.

The Portfolio Optimization tab — how to use it

The first six tabs measure risk. This one acts on it — it asks "given these scenarios, which weights should I actually hold?" and answers with a new set of percentages.

  1. Click Run risk analysis in the sidebar first (this loads prices and your current weights). Then open the 🎯 Portfolio Optimization tab.
  2. Pick a Scenario source:
    • Historical — uses the real return history. No simulation. Best when the future will look roughly like the past.
    • Normal Monte Carlo — uses 5,000 (by default) simulated futures drawn from a Normal model. Smooth baseline, but optimistic for crypto.
    • Student-t Monte Carlo — same idea, but with fat tails. Recommended for crypto.
  3. Set the Horizon (days), MC scenarios, Confidence level, Random seed, and (for Student-t) df.
  4. Pick an Objective:
    • Minimize CVaR — the safest portfolio that still adds up to 100%.
    • Max return under CVaR cap — earn as much as possible while keeping CVaR below the cap you choose.
    • Min CVaR for target return — the least-risky portfolio that still earns at least your target return.
    • CVaR efficient frontier — a sweep of the trade-off between risk and reward.
    • Compare all — runs every objective above and lines them up next to your current portfolio.
  5. Set Constraints:
    • Long-only on (default) — no short-selling.
    • Min / max weight per asset — caps any single position. Setting max = 0.5 prevents the optimiser from going all-in on one coin.
    • Include cash asset — adds a CASH column that earns a constant per-horizon return. Often optimal when other assets look risky.
    • CVaR cap and Target return — only active for the objectives that need them.
  6. Click ▶️ Run optimization.

You'll see five KPI cards (Status, Expected return, Volatility, VaR, CVaR), a sorted table of the new weights, a bar chart of the same weights, a current-vs-optimised risk-comparison table and chart, an allocation-comparison chart, and (if you picked the frontier) a scatter of the CVaR efficient frontier with the min-CVaR and max-return points highlighted.

Every chart and table has a ⬇️ Download button.

If the optimiser says "infeasible": your constraints rule out every possible portfolio at once. The most common cause is a target return that no combination of your assets can achieve. Lower the target, raise the CVaR cap, or relax min/max weight bounds and try again — the app will not crash, it just shows the status and a one-line message.

8. Understanding the numbers

Here is a plain-English explanation of every metric the app shows.

VaR — Value at Risk

"Out of 100 days, how bad is the 5th-worst day likely to be?"

If the app says VaR 95% = 4.2% ($4,200), that means:

  • On 95% of days you should not lose more than 4.2% of your portfolio.
  • On 5% of days — about 1 in 20 — you might lose at least that much.
  • On a $100,000 portfolio, that is at least $4,200.

CVaR — Conditional Value at Risk (also called Expected Shortfall)

"On those bad days, how bad does it get on average?"

VaR tells you the threshold. CVaR tells you the average of all the days that crossed it. CVaR is always at least as big as VaR.

If VaR is the front door of bad days, CVaR is the average room behind that door.

The three VaR methods, explained

MethodWhat it doesWhen to trust it
Historical Sorts past returns from worst to best and reads off the tail. When the future will look like the past.
Gaussian Pretends returns follow a perfect bell curve. For relatively calm assets. Often too optimistic for crypto.
Cornish-Fisher Like Gaussian but corrected for crypto's fatter tails. The most realistic of the three for crypto.

It's normal for the three numbers to differ — that's the whole point of comparing them.

Drawdown

How far the portfolio dropped from its all-time peak. Max drawdown is the worst such drop in the period.

A max drawdown of −72% means there was a moment in the past where the portfolio was worth only 28 cents on the dollar compared to its previous high. Recovery from such drops takes time.

Annualized volatility

A number that summarises how bumpy the ride is over a full year. Higher = more swings up and down. A pure-stocks portfolio might be 15-20%. Crypto portfolios are often 60-100%.

Sharpe ratio

Reward divided by bumpiness. Higher is better.

  • Below 0 — the portfolio lost money on average.
  • Around 0.5 — typical.
  • Above 1.0 — very good.

Backtesting — does the VaR number actually hold up?

A VaR number is only useful if it is actually right. Backtesting is a fairness check: we go back in time, ask the model to predict the loss for each day using only the data it would have had at the time, and then compare with what really happened.

Two things matter:

  • Breaches — days where the actual loss was worse than the VaR prediction. At 95% confidence over 252 days you'd expect about 252 × 5% ≈ 13 breaches. Way more = the model underestimates risk. Way fewer = the model is too pessimistic.
  • Clustering — whether the breaches are spread out evenly or bunched together. A model that gets breaches in clusters has missed the fact that bad days come in waves (volatility regimes).

The three statistical tests

TestWhat it asksYou want
Kupiec POF Is the total number of breaches close to what we expected? p-value ≥ 0.05 means "yes, looks fine".
Christoffersen Independence Are the breaches spread out, or are they clustered on consecutive days? p-value ≥ 0.05 means "no clustering — good".
Conditional Coverage Both at once — a combined verdict. p-value ≥ 0.05 means the model passes overall.

Each test reports a p-value between 0 and 1. The rule of thumb: ≥ 0.05 = pass, < 0.05 = fail.

The traffic light

Borrowed from the Basel III banking regulation. After the tests, the app combines breach count and breach rate into a single colour:

  • 🟢 Green — model looks healthy. Use it.
  • 🟡 Yellow — model is borderline. Take it with a pinch of salt.
  • 🔴 Red — model is unreliable for this portfolio / time period. Pick a different method or look at why.

When the test window is close to the Basel III standard (~250 days), the app uses the regulator's exact thresholds. For longer or shorter windows it falls back to a rate-based version that asks "is the number of breaches within roughly ±25% of what we expected?" — the same idea generalised to any window length.

Horizon-aware backtesting (what changed in Phase 4)

Before Phase 4 the Backtesting tab always ran a daily one-step test, even if the headline cards showed weekly VaR. That was inconsistent. Now the Horizon input drives both the VaR forecast and the realised return:

  • At date t, the model looks at the rolling lookback window before t, aggregates it into rolling h-day returns, and computes the h-day VaR from those.
  • The realised value is the realised h-day return starting at t — not the next single day.
  • A breach is exactly the same idea as before, just at the horizon you actually care about: realised h-day return < − h-day VaR.

Side benefit: now you can answer a real question like "my position is held weekly — how often does my 7-day VaR actually understate the loss?".

Monte Carlo — looking forward instead of backward

Backtesting checks the past. Monte Carlo simulates the future. The idea: take the historical mean returns, volatilities, and correlations of your assets, treat them as the description of a joint distribution, then draw thousands of plausible next-day (or next-7-day, …) outcomes from that distribution. Apply your portfolio weights to each one, look at the left tail, and report the VaR / CVaR.

DistributionWhat it assumesWhen to use it
Normal Returns are bell-shaped. Extreme losses are very rare. As a baseline — usually too optimistic for crypto.
Student-t Returns are bell-shaped in the middle but have fat tails — extreme losses are far more common than a Normal would predict. The honest choice for crypto. The df (degrees of freedom) knob controls how heavy the tails are: df = 4 is very heavy-tailed, df = 30 is almost Normal. Default 5 is a good starting point.

Two important things to remember:

  • Reproducibility. Every simulation accepts a random seed. Same seed = identical scenarios. The default seed is 42, so anyone running the demo gets the same numbers you do.
  • Horizon scaling. For a multi-day horizon h, the Monte Carlo engine multiplies the mean by h and the covariance by h (i.i.d. approximation). That captures the "more days = more dispersion" effect; it does not capture volatility clustering (that's Phase 6, GARCH).

Method comparison — which number to trust

The Monte Carlo tab and the demo both produce a comparison table with five rows. Use it like this:

  • Historical VaR/CVaR — what the past actually did. Good baseline.
  • Gaussian VaR/CVaR — what a Normal model would predict. Usually understates crypto tail risk.
  • Cornish-Fisher VaR — Gaussian with a fat- tail correction. Often the closest parametric match. (No CVaR — listed as N/A.)
  • Normal MC VaR/CVaR — same as Gaussian, but drawn from simulation instead of computed from a formula. Useful as a sanity check.
  • Student-t MC VaR/CVaR — the most conservative number on this list, by design. If your risk tolerance is low, this is the number to act on.

Portfolio value paths

The path chart shows a fan of plausible portfolio trajectories over the next 30 days (configurable). Each translucent line is one simulated future; the solid dark line is the mean across all paths. Reading it:

  • The spread of the fan tells you how uncertain the next month is.
  • If a meaningful share of paths drops below the dashed initial-value line, that's the visual analogue of CVaR.
  • Switching from Normal to Student-t makes the fan wider — that's the fat-tail effect visualised.

From measuring risk to choosing weights (Phase 5)

Up to this point everything is descriptive: the app tells you what the portfolio's risk is. The Phase-5 Optimization tab is prescriptive: it tells you what the portfolio should be, given the scenarios you trust and the constraints you set.

Why CVaR instead of variance (mean-variance) optimisation?

  • Variance treats upside and downside the same. A 20% one-day gain and a 20% one-day loss have identical variance. CVaR only counts the losses.
  • Variance assumes a bell curve. Crypto returns are fat-tailed — the bell curve underestimates the really bad days. CVaR uses whatever distribution the scenarios come from, fat tails included.
  • CVaR is mathematically coherent (it rewards diversification correctly); VaR alone is not.

The four optimisation objectives, plain English

ObjectiveWhat it solves forWhen to use
Minimum CVaR The safest portfolio — minimises the average loss in the worst β-tail. When capital preservation is the priority.
Max return under CVaR cap The most aggressive portfolio whose CVaR is still ≤ the cap you set. "I'll take risk, but not more than X% loss in the tail."
Min CVaR for target return The safest portfolio that still earns at least your target return. "I need at least r% per horizon — minimise everything else."
CVaR efficient frontier A curve of every efficient trade-off between risk and return. To see the full risk/reward menu before picking a point.

Reading the current-vs-optimised comparison

The comparison table shows your current portfolio on row 1 and each optimised portfolio underneath, all measured on the same scenario matrix. Reading the columns:

  • Expected return — average per-horizon return across all scenarios. Bigger is better.
  • Volatility — standard deviation of scenario returns. Smaller is calmer.
  • VaR / CVaR — positive loss numbers. Smaller is safer.
  • Money VaR / CVaR — the same numbers in dollars, given your initial capital.
  • Status — "optimal" means the solver converged. "infeasible" means the constraints couldn't be satisfied (see the warning callout in section 7).

A typical pattern: the Min CVaR portfolio has smaller CVaR and a smaller expected return than your current one (no free lunch). The Max Return under CVaR Cap portfolio sits with CVaR ≈ the cap you chose. The Target Return portfolio earns close to your target with the lowest CVaR possible.

The CVaR efficient frontier chart

Each dot is one optimal portfolio. The x-axis is CVaR (more → riskier); the y-axis is expected return (higher → more profitable). The green dot is the minimum-CVaR portfolio (left-most). The orange dot is the maximum-return portfolio (top-most). Every dot in between is a different valid trade-off — you pick the one that matches your appetite.

9. If something goes wrong

"python3: command not found" or "python is not recognized"

Python is not installed, or Windows didn't add it to PATH. Re-run the Python installer and make sure to tick "Add Python to PATH" on the very first screen.

The terminal says "(.venv)" disappeared after I closed it

That's normal. Every time you reopen the terminal you must re-activate: 

# Windows
.\.venv\Scripts\Activate.ps1

# macOS / Linux
source .venv/bin/activate

"streamlit: command not found"

Either the workspace isn't activated (no (.venv) in the prompt) or the install step didn't complete. Re-run: 

pip install -r requirements.txt

"CoinGecko returned HTTP 429"

The free price service is rate-limited. Either wait a minute and try again, or change Data source in the sidebar to yfinance.

The browser tab didn't open by itself

Open a new tab manually and visit: 

http://localhost:8501

The app shows an error in red after I click Run

The error message itself usually tells you what to fix. The most common ones:

  • "Weights must sum to 1.0" — turn on auto-normalize in the sidebar.
  • "Not enough price data" — pick an earlier start date.
  • "Asset 'X' is missing 'coingecko_id'" — fix the missing ID in the portfolio editor row, or delete that row.

I want to start completely fresh

Delete the .venv folder and the data/cache/ folder, then go through the setup section again from step 2.

If none of this helps: take a screenshot of the error and send it to whoever shared this project with you. Include the last few lines of the terminal output.

10. Glossary

Terminal (also: Command Prompt, PowerShell, Shell)
A text window where you type commands instead of clicking buttons.
Python
A popular programming language. The project is written in it.
pip
The tool Python uses to download and install other packages.
Virtual environment (venv)
An isolated workspace for the project so it can use specific versions of packages without affecting anything else on your computer.
Streamlit
The tool that turns the project's Python code into a web page you interact with in your browser.
CoinGecko / yfinance
Two free services that provide historical crypto prices. The project tries CoinGecko first and falls back to yfinance if needed.
Portfolio
The collection of coins (or stocks) you own and the percentage of your money in each.
Weight
The fraction of your portfolio in one asset. 0.5 = 50%.
Return
How much an asset went up or down over one period, expressed as a percentage. +2% means it gained two percent that day.
Confidence level
How rare the event you're measuring is. 95% means "the loss you will not exceed 95 days out of 100".
VaR
Value at Risk. The loss threshold that should only be crossed on the worst few days.
CVaR (Expected Shortfall)
The average loss on those worst few days.
Drawdown
How far the portfolio has fallen from its previous all-time high.
Backtesting
Replaying history day by day to check whether a risk model would have predicted the right number of bad days.
Breach (or exception)
A day when the actual loss was worse than the VaR prediction. At 95% confidence, about 5% of days should be breaches.
Rolling window
The block of recent past days the model uses to make each new prediction. 252 days ≈ one trading year — the regulatory standard.
p-value
A number between 0 and 1 from a statistical test. In this app the rule is simple: ≥ 0.05 = the model passes, < 0.05 = the model fails.
Kupiec POF / Christoffersen tests
Standard backtesting tests. Kupiec checks the count of breaches; Christoffersen checks whether they are clustered. The Conditional Coverage test combines both.
Traffic light (Basel III)
The regulator's green / yellow / red verdict on a backtested VaR model, based on how many breaches occurred over a ~250-day window.
Horizon (or time horizon)
How far into the future the risk forecast looks. h = 1 is daily; h = 7 is weekly. In the Backtesting and Monte Carlo tabs, this is the Horizon (days) input.
Horizon-aware backtesting
The Phase-4 fix: when the horizon is 7, the backtest compares the realised 7-day forward return against the 7-day VaR forecast, not yesterday's daily return against a daily VaR.
Monte Carlo
A technique that estimates risk by simulating thousands of plausible futures from a probability model, then summarising the simulated loss distribution. Opposite of backtesting, which only looks at the past.
Scenario
One simulated future. The Monte Carlo engine draws 5,000 of them by default.
Normal vs Student-t distribution
Two ways the simulator models returns. Normal = thin tails (extreme losses very rare). Student-t = fat tails (extreme losses much more likely). Crypto markets behave like Student-t.
Degrees of freedom (df)
The tail-heaviness knob for the Student-t simulator. Smaller df → heavier tails. Must be greater than 2 so the variance is finite. Default 5.
Random seed
An integer that pins down the random-number generator. Same seed = identical scenarios every run. Default 42.
Portfolio path
One simulated trajectory of the portfolio's dollar value over the next h days, drawn from the Monte Carlo model.
Portfolio optimisation
The Phase-5 step that chooses weights — instead of just measuring the risk of your current portfolio, it solves for a new one that minimises tail risk, maximises return under a risk cap, or hits a target return as safely as possible.
Scenario matrix
The table of returns the optimiser uses as its picture of the future: rows = scenarios (one per simulated day or one per historical day), columns = assets. It can come from history or from Monte Carlo.
Constraint
A rule the optimiser must obey. Examples: "weights add to 100%", "no shorting" (long-only), "no single asset above 50%", "CVaR must stay below 10%".
Long-only
A constraint that forbids negative weights. You can only own assets, not bet against them.
Cash asset
An optional extra column added to the scenario matrix with a constant per-horizon return (e.g. the daily risk-free rate). The optimiser can put money in cash like any other asset.
Minimum CVaR portfolio
The portfolio with the smallest possible CVaR given your constraints. The safest weights under the chosen risk measure.
CVaR cap
A user-set upper bound on portfolio CVaR. The optimiser chases as much expected return as possible without letting CVaR exceed this value.
Target return
A minimum expected return the optimised portfolio must deliver. The optimiser then picks the lowest-CVaR portfolio that satisfies it.
CVaR efficient frontier
The curve of all portfolios that give the highest expected return at each level of CVaR (or, equivalently, the lowest CVaR at each target return). You pick the point that matches your risk appetite.
Rockafellar-Uryasev formulation
A mathematical trick (Rockafellar & Uryasev, 2000) that turns CVaR optimisation into a linear programme — fast, globally optimal, and easy to solve. The Phase-5 engine uses this under the hood via CVXPY.
Infeasible (optimisation status)
The solver couldn't find any weights that satisfy your constraints all at once (e.g. the target return is so high that no combination of assets can reach it). The app reports the status and keeps running.
Solver (CVXPY / CLARABEL / SCS / ECOS)
The numerical engine that actually crunches the linear programme. The project uses CVXPY as the modelling layer and falls back through CLARABEL → SCS automatically — no commercial solvers required.
localhost
Your own computer, when seen as a website. The web app lives at http://localhost:8501 while it is running.

That's everything you need. If you got the app open and you can read the risk summary table, you've made it. The rest is just exploring different coins, dates, and confidence levels.

## Phase 3 — VaR Backtesting & Model Validation ✅

Convert the engine from a one-shot calculator into a model
*validation* engine aligned with the Basel III market risk framework
(BCBS 2019).

### New module — `backtesting.py` (~570 lines, pure functions, no I/O)

- `rolling_var_forecast(returns, method, confidence_level, window)` —
  strict no-look-ahead one-step-ahead forecast. Slice
  `returns[t-window:t]` excludes `t`. Output length = `len(returns) - window`.
- `calculate_var_breaches(forecast_df, confidence_level)` — counts,
  rates, ratio.
- `kupiec_pof_test(breaches, confidence_level)` — Proportion of Failures
  likelihood ratio, χ² df = 1. Robust at `x = 0` and `x = n` via the
  `0 · log(0) = 0` convention (helper `_xlogx`).
- `christoffersen_independence_test(breaches)` — first-order Markov
  transition matrix, LR χ² df = 1.
- `christoffersen_cc_test(breaches, confidence_level)` — joint test,
  `LR_cc = LR_pof + LR_ind`, χ² df = 2.
- `assign_traffic_light_status(...)` — modes: `basel3`, `rate_based`,
  `auto` (basel3 when 240 ≤ n ≤ 260).
- `interpret_traffic_light_status(status)` — canonical sentence per
  Green / Yellow / Red.
- `backtest_var_model(...)` — orchestrator returning
  `(forecast_df, result_dict)` with 19+ documented keys including
  `traffic_light_mode_used`.
- `compare_var_models_backtest(...)` — multi-method runner. A failure
  in one method records the error in the row and continues; never
  aborts the comparison.
- `create_backtesting_report_table(comparison_df)` — 14-column
  reporting table with ✓ Pass / ✗ Fail / N/A formatting.

### New plots (appended to `plotting.py`)

- `plot_var_backtest` — grey actual line, red dashed −VaR line, red
  ✕ scatter on breaches.

### Fix: horizon-aware backtesting

- `calculate_realized_horizon_returns(returns, horizon_days, method)` —
  forward h-day compounded (`simple`) or summed (`log`) return at each
  index. Last `h` observations dropped (no full forward window).
- `rolling_var_forecast(..., horizon_days, return_method)` — for
  `h > 1` the lookback window is aggregated into rolling h-day returns

## Phase 5 — CVaR Portfolio Optimisation ✅

Turns the project from a pure measurement / simulation platform into
a **portfolio decision-making tool**. Given a scenario return matrix
(historical or Monte Carlo), the new optimisation layer solves for
weights that minimise tail risk, maximise return under a tail-risk
cap, or trace out the CVaR efficient frontier. Built on top of the
Phase-4 scenario engine — no breaking changes to Phase 1–4 APIs.

### Why CVaR rather than mean-variance

- Variance is symmetric (it punishes upside as much as downside);
  CVaR only counts losses.
- Mean-variance assumes Gaussian returns; CVaR optimisation inherits
  whatever distribution the scenarios came from, fat tails included.
- Rockafellar & Uryasev (2000) recast scenario CVaR as a **linear
  programme** — globally optimal, no curvature pathologies, blazing
  fast.

### New module

`src/var_cvar_crypto_risk/optimization.py` — pure analytics (no
plotting, no Streamlit, no I/O). Lazy-imports CVXPY so callers that
only need the validation / builder helpers don't pay the import cost.

Public surface:

- `validate_scenario_matrix(scenario_returns)` — strict input check.
- `add_cash_asset(scenario_returns, cash_return, cash_name)` —
  non-mutating; raises on duplicate column.
- `estimate_expected_returns(scenario_returns, method)` —
  `"mean"` / `"median"` / `"zero"`.
- `calculate_portfolio_scenario_metrics(scenario_returns, weights,
  confidence_level, initial_capital)` — uniform metric dict
  (expected return / vol / VaR / CVaR / worst / best, optional money
  values).
- `format_weights_table(weights)` — descending Asset / Weight table.
- `build_optimization_scenarios(asset_returns, source, n_scenarios,
  horizon_days, student_t_df, random_seed)` — single adapter for the
  three sources (`"historical"` with rolling h-day aggregation,
  `"normal_mc"`, `"student_t_mc"`).
- **Optimisers** (all return a uniform `{status, objective_value,
  weights, expected_return, VaR, CVaR, volatility, solver, message,
  …}` dict and never crash on infeasibility):
  - `minimize_cvar(...)` — Rockafellar-Uryasev LP for the safest
    portfolio.
  - `maximize_return_with_cvar_constraint(..., cvar_limit, ...)` —
    chase return while keeping CVaR ≤ cap.
  - `minimize_cvar_for_target_return(..., target_return, ...)` —
    safest portfolio that still earns ≥ target.
  - `generate_cvar_efficient_frontier(..., n_points, ...)` — sweep
    target returns between the unconstrained min-CVaR and the
    unconstrained max-return endpoint; skips infeasible points and
    records the count in `frontier.attrs["n_infeasible"]`.
- `compare_current_vs_optimized(scenario_returns, current_weights,
  optimized_results, confidence_level, initial_capital)` — tabulates
  current vs each optimised portfolio on the same scenario matrix.

### LP formulation (used inside every optimiser)

```
minimize_{w, t, u}   t + (1 / ((1 − β) · N)) · Σ_i u_i
subject to           u_i ≥ −R_i w − t      ∀ i
                     u_i ≥ 0                ∀ i
                     Σ_j w_j = 1
                     w_j ∈ [w_min, w_max]   (w_j ≥ 0 for long-only)
```

At optimum, `t` is the implicit VaR and the objective is the CVaR.

## How to run

```bash
source .venv/bin/activate
pip install -e . && pip install -r requirements.txt
python run_demo.py                          # Phase 1 + Phase 3 + Phase 4 → outputs/
python run_phase5_optimization_demo.py      # Phase 5 CVaR optimisation → outputs/
streamlit run app.py                        # dashboard (incl. Monte Carlo & Optimisation tabs)
pytest                                      # 147-test regression suite
```
